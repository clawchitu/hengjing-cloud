# 恒境云 部署说明（给 int.cosyhome.com.cn 运维）

本文说明如何把恒境云前端静态包部署到 `int.cosyhome.com.cn` 的 nginx。前端是纯静态单页应用（SPA），没有服务端进程。

> 本文是交付包的部署文档；hvac-demo / hvac-mock 两个测试站的发布方式见 `docs/deploy.md`，与本文无关。

## 1. 交付物

`hengjing-cloud-<版本>-<commit>.zip`（同名 `.sha256` 用于校验），由 `scripts/build-prod.sh` 生成。解压后目录即站点根目录：

```
index.html          入口，不缓存
config.js           运行时配置（后端地址、下发开关），不缓存，部署时只改这一个文件
version.json        版本、commit、构建时间，报问题时对版本用
assets/*            带哈希的 js / css / 字体，长缓存
favicon.svg
```

校验：`shasum -a 256 -c hengjing-cloud-*.zip.sha256`。

## 2. 下发开关（重要）

**生产环境默认禁止一切下发。** 包内 `config.js`：

```js
window.__HJC_CONFIG__ = {
  apiBase: 'https://control.cosyhome.com.cn/v1',
  apiEnv: 'prod',
  dataSource: 'real',
  writeMode: 'off',          // 全部写操作被前端拦截
  writeProjectCodes: []      // 下发白名单为空
}
```

- 页面上所有会改变设备状态的操作（单房间开关与调温、全开全关、新风设置、统一控制批量下发）都会被前端拦截，不会发出请求。读取类功能不受影响。
- 开放下发需要恒境云负责人另行书面确认，确认后才可以修改 `writeMode` 与 `writeProjectCodes`（项目 code 列表）。运维不要自行修改。
- 这是前端层的防护，不能替代后端权限控制。

## 3. 配置项（config.js）

| 项 | 说明 |
| --- | --- |
| `apiBase` | 接口基址。写完整地址（直连方案）或 `/api`（反向代理方案），不带结尾斜杠 |
| `apiEnv` | `'prod'`。基址是相对路径时按此项判断环境 |
| `dataSource` | 必须是 `'real'`（`'mock'` 是演示数据） |
| `writeMode` | `'off'` 全部拦截（默认）；`'test-only'` 仅测试环境放行，在生产等同禁止；`'on'` 生产放行，须负责人确认 |
| `writeProjectCodes` | 下发白名单（项目 code），空数组即拒绝所有下发 |

改完直接生效，不需要重新构建；浏览器因 `config.js` 不缓存，刷新页面即可。

## 4. 两种接入后端的方案

### 方案 A：nginx 反向代理（推荐）

浏览器只访问 `int.cosyhome.com.cn`，同源，无需后端开 CORS。`config.js` 里把 `apiBase` 改为 `/api`（或打包时 `API_BASE=/api scripts/build-prod.sh`）。

```nginx
server {
    listen 443 ssl;
    server_name int.cosyhome.com.cn;
    # ssl_certificate / ssl_certificate_key 按现有配置

    root /srv/hengjing-cloud/current;   # 指向解压后的目录（见第 6 节的目录结构）
    index index.html;

    # 入口和运行时配置：不缓存，每次回源校验
    location = /index.html { add_header Cache-Control "no-cache"; }
    location = /config.js  { add_header Cache-Control "no-store"; }
    location = /version.json { add_header Cache-Control "no-store"; }

    # 带哈希的静态文件：长缓存；不存在就 404，不要回退到 index.html
    location /assets/ {
        add_header Cache-Control "public, max-age=31536000, immutable";
        try_files $uri =404;
    }

    # 反向代理：/api/xxx -> https://control.cosyhome.com.cn/v1/xxx
    location /api/ {
        proxy_pass https://control.cosyhome.com.cn/v1/;   # 结尾斜杠不能省，用来去掉 /api 前缀
        proxy_http_version 1.1;
        proxy_set_header Host control.cosyhome.com.cn;
        proxy_ssl_server_name on;                          # SNI
        proxy_set_header Authorization $http_authorization;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 5s;
        proxy_read_timeout 20s;                            # ctrl 同步消息服务端最长等 10 秒，前端 12 秒超时
        proxy_buffering off;
        add_header Cache-Control "no-store" always;
    }

    # SPA 回退：其他路径（如 /sensors、/thermostat）都返回 index.html
    location / {
        add_header Cache-Control "no-cache";
        try_files $uri $uri/ /index.html;
    }
}
```

要点：
- `proxy_pass` 带路径（`/v1/`）时，nginx 会把匹配的 `/api/` 替换成 `/v1/`。
- 若 nginx 的 `add_header` 写在 location 里，会覆盖上层的同名设置；各 location 里的头请逐个写全（如需统一安全头，复制到每个 location 或用 `include`）。
- 不要把 `/api/` 的请求体、`Authorization` 记入访问日志。

### 方案 B：浏览器直连 control.cosyhome.com.cn

`config.js` 里 `apiBase` 保持 `https://control.cosyhome.com.cn/v1`（包默认值）。nginx 只负责静态文件（上面方案 A 去掉 `location /api/` 即可）。

**前提：后端 `control.cosyhome.com.cn` 必须为 `https://int.cosyhome.com.cn` 开 CORS。** 目前预检（OPTIONS）返回 403，不开则页面无法登录。需要放行：
- 来源：`https://int.cosyhome.com.cn`
- 方法：`GET, POST, OPTIONS`
- 请求头：`Authorization, Content-Type`
- 预检缓存建议 `Access-Control-Max-Age: 600` 以上

同源策略下浏览器不会带 Cookie，登录令牌放在 `Authorization` 头，无需 `Allow-Credentials`。

两种方案选一种即可；拿不准选 A（不依赖后端改 CORS）。

## 5. 缓存头汇总

| 路径 | Cache-Control | 原因 |
| --- | --- | --- |
| `/index.html` 及 SPA 回退 | `no-cache` | 发版后用户立即拿到新入口 |
| `/config.js` | `no-store` | 改配置立即生效 |
| `/version.json` | `no-store` | 核对版本 |
| `/assets/*` | `public, max-age=31536000, immutable` | 文件名含内容哈希，改了就换名 |
| `/api/*`（方案 A） | `no-store` | 接口数据不缓存 |

## 6. 发布与回滚

推荐目录结构，用软链接切换，回滚只需改回链接：

```
/srv/hengjing-cloud/
  releases/
    0.0.0-abc1234/      # 每次发布解压到新目录
    0.0.0-def5678/
  current -> releases/0.0.0-def5678
```

发布：

```sh
cd /srv/hengjing-cloud
shasum -a 256 -c /path/to/hengjing-cloud-0.0.0-def5678.zip.sha256   # 校验
mkdir releases/0.0.0-def5678 && unzip -q /path/to/hengjing-cloud-0.0.0-def5678.zip -d releases/0.0.0-def5678
# 方案 A 时，按需修改 releases/.../config.js 的 apiBase 为 /api
ln -sfn releases/0.0.0-def5678 current.new && mv -Tf current.new current   # 原子切换（Linux；macOS 用 mv -fh）
nginx -t && nginx -s reload     # 只改了站点文件时不需要 reload，仅改 nginx 配置才需要
```

验证：

1. `curl -sI https://int.cosyhome.com.cn/` 返回 200，`Cache-Control: no-cache`。
2. `curl -s https://int.cosyhome.com.cn/version.json` 的 commit 与交付包一致。
3. `curl -s https://int.cosyhome.com.cn/config.js` 里 `writeMode: 'off'`、`writeProjectCodes: []`。
4. 直接访问 `https://int.cosyhome.com.cn/sensors`（刷新子路径）不出现 404。
5. 打开登录页，用只读账号登录能看到项目列表（方案 B 失败时看浏览器控制台是否为 CORS 报错）。

回滚：

```sh
cd /srv/hengjing-cloud
ln -sfn releases/<上一个版本目录> current.new && mv -Tf current.new current
```

无需 reload nginx。因为 `index.html` 不缓存、`assets/` 文件名带哈希，用户刷新页面即回到旧版；旧版本的 `assets/` 目录都保留在各自的 release 目录里，不会互相覆盖。建议至少保留最近 3 个版本。

仅配置回滚：把 `config.js` 恢复为包内原文件即可（解压包里有原件）。

## 7. 注意事项

- 默认部署在域名根路径 `/`。放子路径需要改构建配置（`vite.config.ts` 的 `base`）并重新构建，目前包不支持，如有需要请联系我们。
- 登录与续期走后端 `/auth/*`，其中 `/auth/refresh` 需要带 `Authorization` 头，反向代理不要过滤该头。
- 本包里只含前端；不含任何密钥。`config.js` 是公开文件，不要往里写密钥。
