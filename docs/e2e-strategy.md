# 测试分层策略（通用）

原则来自文章：**给写代码的 agent 能跑的验证，让它贴出运行结果，而不是让评审去推理代码对不对。** 评审能靠「这条 e2e 跑过了」放心的地方越多，评审就越不用在时序和边界上反复推演。

我们现在有第 0–2 层，缺第 3–5 层。本文定义每一层，项目落地版见 `hengjing.md`、`yuanhui.md`。

## 0. 定位：测试是正确性的主防线（Shuai，11/25）
e2e 与单元测试共同「钉住」正确性：每条用户流程、每条下发规则都要有对应用例；评审依赖测试结果，而不是代替测试。新增或修改规则时，先补测试再改代码。

## 1. 分层总表

| 层 | 内容 | 连什么 | 在哪跑 | 什么时候跑 | 拦合并吗 | 谁维护 |
|---|---|---|---|---|---|---|
| 0 静态 | 规范检查、类型检查、构建 | 不连 | GitHub 托管 runner | 每个 PR、每次推送 | 拦 | 作者随改动更新 |
| 1 单元与契约 | 纯逻辑、算法向量、协议编解码、服务端连真数据库的接口测试 | 本地或 CI 的数据库，不连外部 | GitHub 托管 runner | 每个 PR | 拦 | 作者；算法向量由规则负责人定 |
| 2 界面（假数据） | 截图对比、组件交互、XCUITest 用夹具数据 | 假数据、拦截的假响应 | 恒境云：Playwright 官方镜像；元辉：Mac mini 自建 runner | 每个 PR（元辉按路径触发） | 拦 | 页面负责人；基线按队列更新 |
| 3 本机全链路 | 真前端或真 App + 真服务端 + 真数据库，全部在本机起 | 本机起的服务 | Mac mini | 改到对应路径的 PR 自动跑；每晚一次 | 高风险 PR 拦 | 把关人维护框架；功能作者补用例 |
| 4 测试服只读 | 真前端连真实测试服，只做读和「验证拦截」 | 真实测试服 | Mac mini（账号在钥匙串里） | 每晚一次；高风险 PR 手动触发一次；发版前 | 稳定后对高风险 PR 拦 | 把关人 |
| 5 测试服真实写入 | 对指定测试对象真实写入，写前读、写后读、恢复 | 真实测试服 + 真设备 | Mac mini，只能手动触发 | 改写路径的 PR 合并前；发版前 | 写路径 PR 拦 | 把关人；每次运行前在群里通知 |
| 6 人工走查和真机 | 按清单在真实站点或真机上完整走一遍 | 真实环境 | 人或 agent 操作浏览器、真机 | 交付或发版前 | 发版拦 | 把关人 |

说明：
- 第 0–2 层必须稳定、快、不依赖外部，所以继续留在每个 PR 的必需 CI 里。
- 第 3–5 层依赖外部环境，**不放进 GitHub 托管的必需 CI**（没有钥匙串、连真实后端有误写风险），单独一个工作流跑在 Mac mini 上，结果作为 PR 评论或运行链接附在 PR 里，由合并脚本或把关人检查。
- **例外（恒境云第 4 层，负责人 11/25 同意仓库公开后定）**：恒境云的第 4 层可以在 GitHub 托管 runner 上跑，条件是：仓库公开；工作流只能手动触发；账号放在 GitHub environment（`h1-live`）的 secrets 里，environment 设必需审批人、只允许 `main` 部署；不进必需 CI。适用范围只限第 4 层（只读）；第 5 层（真实写入）仍按本文在 Mac mini 上跑。公开仓库的 Actions 日志和 artifact 任何人可见，所以只上传去敏的报告、保留 1 天。见 `docs/H1-测试服只读e2e.md`。
- 每一层只测它该测的：第 4、5 层只覆盖「假数据测不出来」的东西（接口真实返回的形状、权限、会话、设备回读），不在真实环境上重复测文案和样式。

## 2. 每层要写什么样的测试

- **第 3–5 层的用例按「用户流程」写**，一条流程是一段完整的业务动作（登录 → 选项目 → 改温度 → 看到已生效）。每个项目维护一张流程清单（见项目落地版），每条流程标明它在哪一层自动化、还是只在第 6 层人工走。
- **断言写「不变量」而不是具体数值**：真实环境的数据会变。例如「列表总数等于各页之和」「在线项目的页面没有 65536」「经销商看不到别家项目」，而不是「项目数等于 433」。
- **网络层守卫**：第 4 层的所有用例都在浏览器网络层或客户端拦截器里挂一个守卫：凡是写接口的请求一律中止并让测试失败。这样即使代码有 bug，只读测试也不可能写到设备。
- **失败时留证据**：截图、网络记录（去掉令牌和密码）、接口回包摘要，上传为运行产物。

## 3. 不稳定的测试怎么处理

1. **拦合并的层（0–2）不允许重试掩盖**：重试次数设 0。一个测试同一提交上一次过一次不过，就算不稳定。
2. **发现不稳定**：任何人发现后，在 `e2e/QUARANTINE.md`（或项目约定的文件）登记一行：测试名、现象、首次发现日期、负责人、截止日期（3 个工作日内）。登记后可以把这个测试标成跳过，但只能跳过登记过的那一条。
3. **截止日期到了还没修好**：要么删掉这个测试并说明它原来覆盖的流程由哪里补上，要么由把关人延期一次。不允许长期跳过。
4. **第 3–5 层先分清「环境问题」还是「代码问题」**：每次运行先跑一步环境预检（测试服能否登录、测试项目是否在线、测试店是否存在），预检不过就把这次运行标记为「环境不可用」，不算失败，也不算通过。环境问题累计记录，用来找后端要长期在线的测试设备。
5. **新的第 4、5 层用例先「只报告不拦」两周**：每晚跑，失败率低于 2% 且没有误报后，才对高风险 PR 改为拦合并。
6. **时间相关的不稳定**（轮询、回读延迟）：用例里用「最长等待 + 轮询条件」，不用固定等待；等待上限与产品口径一致（例如恒境云回读按 5 秒、20 秒、60 秒退避）。

## 4. 测试账号和测试数据

- **账号专用**：自动化测试用专门的账号，不和人工联调、走查共用。原因：恒境云后端每个用户只有一个有效 refresh_token，一登录就挤掉别处的会话；元辉错 5 次密码会锁号 15 分钟。
- **每个账号同时只跑一个任务**：第 3–5 层的工作流用同一个并发组，排队跑，不并行。
- **密码只在钥匙串里**：测试从钥匙串读，经环境变量传给测试进程，不写文件、不打印、不进日志和截图。日志里只打印数量、编码和布尔值。（恒境云第 4 层在托管 runner 上时，账号来自 environment secrets，同样经环境变量传入，见上面第 1 节的例外。）
- **测试数据可识别**：自动化创建的数据名称带固定前缀（例如「E2E-」），并且能一键清理或重置。
- **只在测试对象上写**：能写的对象（测试项目、测试店）列在仓库里的一个清单文件中，测试代码和产品代码的写防护都按这个清单判断。
- **基线快照**：写入类用例运行前记录被改对象的当前状态，结束时（包括失败和中途退出）恢复，并记录恢复后的读数。
- **不连生产**：测试代码启动时断言目标是测试环境（检查地址和环境标识），不是就立即退出。

## 5. 真实写入设备时的安全护栏（第 5 层）

真实写入会影响真实设备，护栏要多层叠加，任何一层单独失效都不会误写：

1. **只能手动触发**：工作流只允许手动触发（不由推送或定时触发），触发时必须填写本次要写的项目和用例。
2. **环境断言**：测试进程启动时断言 API 地址是测试服、环境标识是「测试」，否则退出。
3. **双重白名单**：产品代码的写防护（项目白名单）照常生效；测试代码在每次写之前再自己核对一次目标项目在白名单里。两者都通过才发。
4. **只做可恢复的操作**：只测能改回去的写入（例如设定温度改 0.5 度再改回、开关拨一下再拨回），不测不可逆的操作。
5. **写前读、写后读、恢复、恢复后读**：四步缺一不可；写前读到的状态不符合预期（例如设备离线、有人正在用）就跳过这条用例，不硬写。
6. **次数上限**：每次运行最多写 N 次（项目落地版定，例如 10 次），超过立即停止。
7. **互斥**：同一时间只允许一个写入任务（工作流并发组 + 测试服上的写锁），也不和人工下发测试同时进行。
8. **通知**：运行开始和结束时自动在项目群里发一条消息（谁、哪个项目、写什么、结果）。
9. **时段**：只在约定时段跑（例如工作日白天，后端和现场有人可以响应）。
10. **紧急停止**：有一个不需要发版就能关掉所有写入的开关（例如测试站的运行时配置改成禁止写入），并写进 runbook。
11. **全程留档**：每次写入的请求、回包、写前写后读数，作为运行产物保存，并附在相关 PR 里。

## 6. 和评审规则的配合

- 高风险 PR 的评审门槛（review-policy.md 第 3 节第 5 条）要求附第 4 层或第 5 层的运行记录。
- 评审者看到有对应的 e2e 记录覆盖某个流程时，对这个流程的意见必须给出「e2e 为什么没测出来」的说明，否则按「建议」处理。这条用来减少评审对已验证流程的反复推演。
- 评审提出的「必须修」，修完后对应的失败测试留在仓库里，作为该问题类别的回归测试。
- 每次真实环境发现的问题，复盘时决定补在哪一层，补完在流程清单里登记。
