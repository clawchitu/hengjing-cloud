## 后端答复后的结论（11/25 08:56）

原文见 `projects/hengjing/questions-1125-send.txt` 末尾「后端答复 11/25 08:56」。和这两次实测有关的几条：

1. **上午两次实测读到的「未变化」不能当作下发没生效。** 后端答复第 1 条：控制屏没有上报房间状态，200 里的房间开关读到的是默认值 0，房间实际是开的，后端会修。所以 00:20 的 203「全部开启」和 05:40 的 201「开启」之后读到的 0，只说明开关没有上报，不说明指令没执行。两次的结果都应改记为「无法核对」。
2. 前端已按这条加开关 `features.roomSwitchReported`（默认 `false`，后端修好后改 `true`）。为 `false` 时：房间开关显示「未知」，201 / 203 / 206 的开关核对一律记无法核对，也不再拿它禁用温度、节能（温控「房间关着只能开房间」、统一控制「房间全关」）。
3. 待后端回答第 4、5 条（末端）：第 3 条答复——改了末端就完整回传全部末端，没改就传空列表；末端 switch 是状态显示、由控制屏控制，前端不能改。现在 201 没改末端一律传空列表，不再原样回传读到的末端。上表里「房间开关 0、末端风盘 / 顶辐射 switch 1」，与「房间实际是开的」一致。
4. 待后端回答第 1 条（success 的含义）仍未答复，口径照旧：success 只算已下发，生效只认回读一致。
5. 后端之后说房间状态上报已修好，但第三节 09:07 的只读复核只返回 1 个房间、开关仍是 0，修好与否还没确认。所以 `roomSwitchReported` 仍默认 `false`。下次真机复测前，先和后端 / 现场确认房间开关读数可信，再把测试站 config.js 的 `features.roomSwitchReported` 改成 `true`；否则开关仍然无法核对。
