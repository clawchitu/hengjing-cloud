## Q4 令牌与错误体

### ① permission_paths 与网关

/me 的 `permission_paths` 是 `/v1/...` 形式的路由模板（含 `{id}`），共 578（平台）/ 347（经销商）条。**网关按它拦截**：路由不在列表里，就返回 `403 text/plain "no permission"`。

恒境云用到的接口，在经销商列表里的情况：

| 有权限 | 无权限（实测返回 403 no permission） |
| --- | --- |
| auth/login、refresh、invalidate，/me，/projects，/integrated-projects，/distributors，/apps | /weather、/weather24、/wx/city-list、/projects/frequent、/project/click/{id}、/integrated-projects/stat、/ctrl/unified-ctrls-send、/ctrl/unified-ctrls-records、**ctrl 200–210 全部 11 个** |

平台账号以上全有。

**结论：** 前端 `can(path)` 直接拿路由模板匹配就行，不需要另造映射。但是**测试经销商账号目前用不了首页天气、常用项目、集成统计、全部设备页和统一控制**，需要后端给经销商角色补上这些 path（或说明经销商本来就不应该用这些功能）。

### ② refresh_token

| 步骤 | 结果 |
| --- | --- |
| `POST /auth/refresh {refresh_token}`，**不带** Authorization（按文档） | `401 {"code":16,"message":"no token"}` |
| 同上，带 `Authorization: Bearer <当前 access_token>` | 200，返回新的 access_token 和新的 refresh_token（两者都和旧值不同），`expires_in=7200` |
| 用 camelCase 的 `refreshToken` | 401 no token（字段名只认 snake_case） |
| 再用一次旧 refresh_token | `401 {"code":16,"message":"invalid refresh_token"}`，**旧的已作废（轮换）** |
| 刷新后用旧 access_token 调 /me | 200，旧 access 在过期前仍然可用 |
| Authorization 放垃圾值、空 Bearer、或者放 refresh_token 本身 | `401 {"code":16,"message":"token is not valid 1, jwt.ParseWithClaims failed, ..."}` |
| 用别的会话的 access_token 当 Authorization 去刷新本会话 | 200（头里只要是同一用户的有效 JWT 就行） |
| 同一账号先登录 L1，再登录 L2，然后刷新 L1 | **`401 invalid refresh_token`**；L2 刷新正常；L1 的 access 在过期前仍能用 |

**结论：**
- `/auth/refresh` 实际上**必须带 Authorization: Bearer access_token**，和文档说的「无需 Authorization」不一致。
- 刷新令牌每用一次就换新，旧的立即作废。
- **一个用户同时只有一个有效的 refresh_token**：新登录会让之前所有会话的 refresh 失效。多标签页共享存储不受影响；但多台设备同时登录时，旧设备最迟 2 小时后会被踢出。
- **还没测到的点**：access_token **过期后**能不能放进头里换新。要等 2 小时，这次没测。如果不行，前端必须在过期前主动续期（比如剩 5 分钟时刷新），并且问后端（见末尾）。

### ③ 错误体格式（实测汇总）

| 场景 | HTTP | Content-Type | 体 |
| --- | --- | --- | --- |
| 不带令牌 / 令牌是乱码 / 签名被改 / 没有 `Bearer ` 前缀 | **403**（不是 401） | text/plain | `token err` |
| 路由不在 permission_paths、路由不存在、`/project/notanid` | 403 | text/plain | `no permission` |
| 密码错误 | 401 | application/json | `{"code":16,"message":"密码错误，请重试"}` |
| refresh 失败 | 401 | json | `{"code":16,"message":"no token" / "invalid refresh_token" / "token is not valid 1, ..."}` |
| 不存在的项目 `GET /project/000000000000000000000000` | **500**（没有 404） | json | `{"code":13,"message":"项目信息查询失败"}` |
| 天气 / isdp 被拒等业务错误 | 500 | json | `{"code":13,"message":"..."}` |
| ctrl 读：控制屏离线、项目 id 不存在或非法 | 503 | json | `{"code":14,"message":"控制屏消息发送失败"}`（约 0.7 秒就返回，不会等满 10 秒） |
| ctrl 读：业务失败（设备 id 错、软件类型不支持） | **200** | json | `{"body": ...}`，Reply 的 **#2 字段是错误文案字符串**，例如 `错误的传感器id`、`该软件类型不支持此控制`（文档没写这个字段） |

**结论：** JSON 错误统一是 `{code, message}`，`code` 用的是 gRPC 码（13 Internal、14 Unavailable、16 Unauthenticated），HTTP 状态按 gRPC 码映射，**没有 404**。网关层的错误是纯文本，而且令牌失效返回的是 **403 `token err`**，不是 401。所以前端判断「需要续期或重新登录」要按「403 且 body=token err」，或「401 且 code=16」，不能只看 401。ctrl 的业务错误要解 Reply 的 #2 字段，不能只看 HTTP 状态。

## Q7 ctrl 读接口

公共请求：`POST /v1/ctrl/<route> {project_id, user_id, body: base64}`，对象是在线项目 测试项目0829，用平台账号。

- `user_id` 不传或传错值也返回 200，**服务端不校验**。
- 返回的 `body` 是带换行的 base64（每 76 个字符一个 `\n`），解码前要去掉空白字符。
- 单次耗时 0.7–1.9 秒。

### 解码结果（字段号 → 推测含义）

- **200 房间温控**（1 个房间）：#1 id=406658286、#2 name=房间11、#3 temperature=22.0、#4 humidity=60.0、#5 dew_point=13.9、#6 set_temp=25.5、**#8=3**（推测是 wind_speed）、#15 end_modes ×3（风盘 / 顶辐射 type=1 / 地冷 type=3；其中 #3=is_selected、#4=is_change 都是 1）、#16 is_connected=1。#7、#9–#14 没有出现（值为 0 时 proto3 不输出）。文档列的字段只有 13 个，字段号却跳到了 16，**说明字段号不连续，不能靠猜，Q1 仍然必须拿到 proto**。
- **202 新风除湿机**（1 台）：#1 id=9326461980、#8=20、#9=100、#10=1、#12=`除湿`、#13=2、#15=1。如果按文档顺序，分别对应 dehumidifier_freq=20、filter_life=100、filter_life_p=1、running_mode=除湿、running_time=2、is_connected=1。这里 filter_life 和 filter_life_p 看起来像是反了，无法确认。
- **205 设备汇总**（6 条）：#2 名称、#3 型号、#4 地址、#5 conn_status=1。#1 device_id 都没有出现（值为 0）。设备分别是：网络HUB/485网络集线器、房间11/房间面板、KC2/空气传感器、CS10/集中控制器、TXFS500/空气处理机、空调/空调主机。
- **207 空气传感器**（1 个 KC2）：#1 name、#2 id=2042830592、#3 temperature=25.5、#4 humidity=55、#5 pm2_5=5、#6 co2=580、#7 dew_point=15.8、#8 is_connected=1，和文档顺序完全一致。
- **210**（device_id 用 202 的 id）：Reply 只有 #2 = `该软件类型不支持此控制`（因为这是 app 1 项目，符合预期；没有在线的 app 12 项目可测）。

### ① 208/209 时间单位与跨度

| 请求（Query #1 device_id、#2 start、#3 end） | 结果 |
| --- | --- |
| 208，传感器 2042830592，最近 1 天，**秒** | 200，空 Reply |
| 208，最近 1 天，**毫秒** | 200，2 条 |
| 209，房间面板 406658286，秒 / 毫秒 | 和 208 一样：秒为空，毫秒 2 条 |

| 208，设备 id 不存在 | 200，Reply #2=`错误的传感器id` |

每条记录：#1 id、#2 date=该小时起点的**毫秒**时间戳、#3 hour=**北京时间**小时数（date 1795474800000 = 11/24 07:00 CST，hour=7）、#4 temperature、#6 humidity、#7 dew_point、#8 co2、#9 pm2_5。#5 floor_temperature 没有出现，也就是值为 0，**不是文档说的 -100**。

### ② 无 PM2.5 / CO₂ 探头

唯一在线的传感器 KC2 两种探头都有（pm2_5=5、co2=580），**没有无探头的设备可测**。旁证：
- 208 里没有数据的 floor_temperature 返回 0（字段缺省），不是 -100。前端要考虑「缺省 = 0」也可能表示无效。
- 209 房间面板的小时数据里也带了 co2=580、pm2_5=5，和传感器的值一样，看起来是项目级合并后的数据，不是面板自己测的。

**结论：仍需后端说明。**

### ③ 200 的 wind_speed

只有 1 个房间的样本，#8=3（推测为 wind_speed）。**单个样本推不出档位对应关系，仍需后端说明**（3 表示几档，最大档是多少，100 为自动）。

### ⑤ 刷新频率

单次请求 0.7–1.9 秒。离线项目 0.7 秒就返回 503，所以轮询离线项目不会卡住。频率能不能接受，仍要后端判断。

## Q9 项目字段

- `code`：433 个项目都有，格式像 `YYMMDD+3位序号`（261102001、240829001），**唯一**。
- `number`：433 个里只有 12 个填了，值像 `22222`、`20240514`、`202504098888`，而且有重复，是自由填写的。**结论：「项目 ID」显示 code。**
- 应用名称：`ProjectEntity` 自带 `app_code / app_name`（通用版、独立空气系统……）。`IntegratedProjectEntity` 只有 `app_id`（code 1 那个集成项目连 app_id 都没有）。`POST /apps {}` 两个账号都能调，返回 11 条 `{id, code, name, category_id, category_name, remark}`，例如 `6aa3a051… / 12 / 独立空气系统`、`62415e11… / 1 / 通用版`。**结论：集成项目卡的类型名称用 /apps 按 app_id 查。**
- `brief_stat`：只有 `device_count`、`room_count`（都是字符串），**没有温度、湿度、CO₂**。只有 62/433 个项目有这个字段。**结论：常用项目卡去掉温湿度和 CO₂ 那一行，或改为显示设备数 / 房间数。**
- 在线状态：`online` **只在 true 时出现**（proto3 的 false 不输出），缺失就当离线处理。另有 `GET /ctrl-mode/online-project-id-list` → `{"ids":[...]}`，两个账号都能调。**没有最后在线时间字段**（ProjectEntity 里没有这类字段）。
