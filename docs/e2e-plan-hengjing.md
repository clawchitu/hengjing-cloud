# 恒境云落地版

仓库：`~/code/hengjing-cloud`（`clawchitu/hengjing-cloud`）。React + Vite 网页，暖通 IoT 控制台。
测试服：`https://test.cosyhome.com.cn:9443/v1`；测试站 hvac-demo（`hvac-demo.haoqianglyu.com`，Worker 把 `/api` 转发到测试服）。
写接口 5 个：ctrl 201（房间温度设置）、203（统一控制设置）、204（运行设置）、206（全部房间开关）、`unified-ctrls-send`，全部经过 `src/api/guard.ts`。可下发的测试项目只有 260911001、240829001（`DEFAULT_WRITE_PROJECT_CODES`）。

本文件的第 1–4 节就是仓库 `REVIEW.md` 第 12 节「项目专项」的内容；通用部分照抄 `review-policy.md`。

- CI（`.github/workflows/ci.yml`）：oxlint、`tsc -b`、vitest、vite build；Playwright 截图对比（演示数据，逐像素严格）。不连任何真实后端（plan-v1 §3.6 规定）。

## 1. 必须修的类别（拦合并只限这 6 类）

| # | 类别 | 算 | 不算 |
|---|---|---|---|
| A | **误下发** | 白名单外的项目、生产环境、错项目、错房间、错值被发出去；绕过 `guard.ts` 或统一写入口；没经确认就发；用确认前的旧读数组装请求（例如 `end_modes` 传空列表） | 写防护已经拦住的路径上缺少再一次检查 |
| B | **下发结果误报** | 没有回读一致就提示「已生效」、清草稿或放写锁；把「结果未知」判成「未下发」导致用户重复下发；四态结论与 `docs/分工.md` 第 4 节口径相反 | 结论正确但提示出现得短暂偏早或偏晚；文案措辞 |
| C | **越权和泄漏** | 经销商看到别家的项目或记录；令牌、手机号、密码进日志、URL、截图、PR；Worker 转发能被绕到非测试服或非白名单路径 | 前端隐藏了按钮但后端也会拒绝的情况下，按钮多显示了一会儿 |
| D | **会话失效处理错** | 登录不了；续期循环、反复踢掉自己；403「no permission」被当成登录失效踢回登录页；退出后后退还能看到数据 | 多一次续期请求 |
| E | **白屏、崩溃、卡死** | 页面白屏、未捕获异常、无限转圈、按钮永久不可点 | 加载态多闪一下 |
| F | **错误数据会误导操作** | 显示 65536 等无效值；离线项目显示旧数据当成当前值；切换项目或经销商后残留上一个的数据；数值和单位算错 | 刷新慢几秒 |

规则沿用：同类时序意见要有能跑的复现，后果要超出「展示短暂偏早」才受理（`docs/HANDOFF.md` 1.3 收口规则）。

## 3. 写路径专项清单（评审逐条过，在总评「已核对」里逐条写结果）

1. 所有写请求经过 S4 统一写入口和 `guard.ts`，没有直接 `fetch` 写接口。
2. 确认弹窗在真正发起下发的组件里取（`docs/分工.md` 第 3 节第 7 条）。
3. 写入口前判空当前项目（第 6 条）。
4. 请求体由**确认之后新读的**数据组装；`end_modes` 原样回传，读不到就禁用（HANDOFF 1.1）。
5. `claim` 在 `beforeSend` 链的最后；发送前 `checkSentRecord`（HANDOFF 1.2）。
6. 写结果分类复用 `outcomeOf`：只有 503 + code 14、写防护、401、认领前出错算「未下发」。
7. 成功提示、清草稿、写缓存都在写锁认可的 `commit` 里（HANDOFF 1.3）。
8. 四态和文案与 `docs/分工.md` 第 4 节表格一致；优先级只在 `verdictOf` 一处定义。
9. 目标 id 在原始回包里恰好出现一次，确认前和预检各查一次；回读里 id 重复或无效判「无法核对」。**这一条是 #35 里反复出现的问题类别，第 1 轮就要搜遍所有写路径。**
10. 规则草稿（`docs/使用说明-规则草稿-*.md`）在同一 PR 里更新。
11. 附第 4 层（只读）和第 5 层（真实下发）运行记录；没有的，评审第一行写「门槛未满足」。

### 不要再提（已裁定或已知误报）

- 「展示短暂偏早或偏晚」类时序意见（HANDOFF 1.3）。
- proto3 标量缺省 = 0 被当作真实读数（这是口径，`docs/分工.md` 第 4 节）。
- 写防护已拦截的路径上再加一层检查。
- 与 Fable 已裁定的口径（四态优先级 B、`commit` 可否决提交）相反的建议，除非附新的实测记录。

## 5. 恒境云特有的护栏（在 e2e-strategy.md 第 5 节之上）

- 第 4 层每个用例在 Playwright 的网络层挂守卫：URL 命中 `guard.ts` 的 `isWritePath` 同一套规则（5 个写接口，以及 `ctrl/*-set`、`*-send`、`*-ctrl-message`）就中止请求并让测试失败。守卫写成共用夹具，所有只读用例默认带上。
- 第 5 层只能通过手动触发运行，并且需要显式传入 `HJC_E2E_WRITE=1` 和目标项目编码；测试代码在每次下发前自己核对目标在 `DEFAULT_WRITE_PROJECT_CODES` 里。
- 每次运行最多 10 次下发，每个项目最多 5 次；S9、S10、S12 的人工下发测试时段不重叠（`docs/分工.md` 第 3 节第 5 条）。
- 下发前后自动在项目群里发一条消息。
- 紧急停止：hvac-demo 的 `/config.js` 由 Worker 生成，加一个 Worker 变量可把 `writeMode` 改成 `off`，无需重新构建（写进 `docs/部署说明.md`）。
- 账号：现在钥匙串里有两套名字（`hengjing-admin` / `hengjing-dealer` 和 `hengjing-test-platform` / `hengjing-test-dealer`），先统一。后端每个用户只有一个有效 refresh_token，自动化测试会挤掉同账号的人工会话，所以**向后端要一个自动化专用的平台账号和经销商账号**；要到之前，自动化只在没人走查时跑，并且串行。
- 和 plan-v1 §3.6「CI 里的测试一律用拦截的假响应，不连任何真实后端」的关系：第 4、5 层不进必需 CI，在本机或 Mac mini 上跑，不违反这条；但第 5 层是新的真实写入入口，开工前请负责人确认一次。
