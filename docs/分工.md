## 4. 下发结果口径（11/24 实测后修订，Fable 裁定）

起因：11/24 在测试服下发 203「全部开启」返回 success=true，但 23 秒、90 秒两次回读 200，房间仍是关。

1. **success 只表示已下发，生效只认回读一致。** 写入口返回 success（201 / 203 / 204 / 206）后进入「已下发，待核对」，回读与下发目标一致才算已生效。
2. **结果四态**，逐字段判，后三态都锁到核对一致或写锁有效期到期（到期发强制重读），不提前放、不续期；核对不是一致时，有效期内按 5 秒、20 秒、60 秒自动重新核对：
   - **已生效**：回读读到且与目标一致。
   - **未变化**：回读读到但与目标不一致。指令已下发、设备状态暂未变化，不写「失败」。未变化不等于没生效，前提是比对对象正确。
   - **无法核对**：整个目标房间条目缺失；回包成功但为空（如 `{}`）；写入目标在 200 里没有对应字段（统一控制的系统开关、运行模式）。读数无效（-100 无效数据、65536 未初始化、-1）按设备没回报，也算无法核对；0 是有效读数（后端 11/25 答复第 9 条）。房间开关未上报期间（`features.roomSwitchReported = false`，11/25 第 1 条）房间开关一律无法核对。可核对字段见 `src/api/writeLockVerify.ts` 的 `VERIFIABLE_FIELDS`（201 / 206 的 switch、set_temp、eco 可核对）。
   - **结果未知**：回读请求失败（网络错误、超时、非 2xx、控制屏离线），或目标房间面板离线（读数不可信）。提示重试，不并入无法核对。
   - **混合字段**：整体结论按最坏的确定结论，**结果未知 > 未变化 > 无法核对 > 已生效**（Fable 裁定 B：未变化是回读确认的不一致，无法核对只是缺证据；回读失败时每个字段都无证据，结果未知最前）。整体结论只作标题，逐字段结果照列，混合时写成「1 项未生效，1 项无法核对」。优先级只在 `writeLockVerify.ts` 的 `verdictOf` 一处定义；写锁的 `lastFields` 给出逐字段结果。
   - **放锁**：只有所有目标字段都回读一致才放锁（或有效期到期）。
3. **成功提示只在核对一致后弹出。**

比对口径：200 的 switch、set_temp、eco 等是 proto3 普通标量，0 在线上本来就省略，解码出的 0 就是真实读数（缺省 = 0），直接比对。实现见 `src/api/writeLock.ts` 文件头口径 4、`src/api/writeLockVerify.ts`（与统一控制 `src/features/unified/batch.ts` 的 `summarizeRooms` 同一套读数规则）。
