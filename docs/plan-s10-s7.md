## 0. 结论

1. 共 6 个 PR：1 个公共准备、S10 三段、S7 两段。前 3 个不动界面和基线，现在就能做，不依赖后端回复。
2. 所有等后端回复的点都收进一组运行时开关（`config.js` 的 `features`），回复后只改开关默认值或一个映射函数。
3. 原方案的「city-list 与省市级联取交集」改为：级联数据是候选全集，city-list 只在调用成功时用来过滤，调用不了就不过滤；项目所在城市始终可选。这样经销商有城市可选。这是对原方案的改动，需要负责人确认（见 3.1）。
4. 204 的「不变」表示法，回复前默认用「把确认后新读的 210 原样带回」，不用 -1。理由见 2.3，需要赤兔确认。
5. 真机验证最大的不确定：两个测试项目共用一块屏，这块屏在 240829001 上对 210 回的是「该软件类型不支持此控制」。260911001 走同一块屏，210 很可能也读不出设置。只读摸底第一步就验证这一点。

### S7a 天气数据层

范围（新目录 `src/features/weather/`）：
- `model.ts`：`/weather` 的 `now`、`f1`–`f7` 和 `/weather24` 的 `hourList` → 视图模型。所有字段可缺，缺了就是 `null`，界面据此隐藏。解析 `sd`（`51%`）、`air_press`（`1031.3 hPa`）、`sun_begin_end`（`06:31|16:56`）、`wind_power`（`0-3级 <5.4m/s`）、`time`（`201611061000`）。字段以 `docs/api/weather-sample-320500.json` 为准。
- `dew.ts`：由温度和相对湿度算露点（Magnus 公式）。拿到 cosydata_fable 的 `utils/dewPoint.js` 后对一遍结果，不一致以它为准。
- `cities.ts`：省 → 市两级数据和查询函数。数据来自 cosydata_fable 的 `cascader_disdrict.js`，裁到市级，做成单独的懒加载分块。拿不到这个文件时用国标行政区划（GB/T 2260）的公开数据生成，结构相同。
- `citySource.ts`：候选城市的来源和过滤，见 3.1。
- `cityStore.ts`：上次选择的读写（localStorage，按用户 id 分键，读取时校验结构和编码是否还在候选里）。
- `source.ts`：`real` 和 `mock`。实时加 7 天、24 小时是两个独立请求，状态各自独立。
- `hooks.ts`：`useWeatherNow(city)`、`useWeather24(city)`、`useCityOptions()`、`useWeatherCity()`。`staleTime` 30 分钟（服务端按 city 缓存 30 分钟）。读请求沿用全局的「服务器错误重试 1 次」，覆盖无锡首次请求偶发 500。
- 权限：`can('/v1/weather')`、`can('/v1/weather24')`、`can('/v1/wx/city-list')` 分别判断。

验收：界面零变化；经销商账号（三个接口都 403）不发天气请求。

测试要点（vitest）：

- 解析：日出日落、气压、湿度、风力、小时时间；`ret_code` 非 0 映射成「未查到该城市天气」。

### S10c 新风运行设置下发

范围：
- `src/features/freshAir/edit.ts`：草稿和读数分开；`build204(draft, fresh210, policy)` 是唯一的组装点；可改项的判断在 `editBlock`。

写路径逐条对照 S9（`docs/HANDOFF.md` 第 1 节）：

| 环节 | S10 的做法 |
| --- | --- |
| 确认 | 在 `FreshAir.tsx` 里取 `useConfirm()`，不从父组件传。确认文案写明项目名、项目 code、设备名和逐项「原值 → 新值」 |
| 加锁 | 用户点了确认之后再 `acquire(project)`，返回 busy 时提示同屏有下发在进行。`target` 的 `fa:<设备 id>` 只是结果条上的标签，锁仍然是 `acquire(project)` 按控制屏加，和 201、203、206 互斥 |
| 预检 | 确认后新读 210 和 202。202 原始回包里目标设备 id 恰好出现一次；设备在线；210 的 `id` 相符；用户没改的字段与确认时的读数相同，否则不发并提示「读数已变化」 |
| 组装 | 用预检读到的 210 调 `build204`，不用弹窗前的读数。`name` 取预检读到的值 |
| 发送前 | `checkSentRecord(record)` 不过就 `release` 并提示原因 |
| beforeSend | `sameSession() && sameProject() && present() && claim(token)`，claim 在最后。这是 `runOp` 已有的实现 |
| 登记 | 拿到 Promise 立刻 `markSent(token, p, record)` |
| 结果分类 | `classify` 复用 `outcomeOf` |
| 核对 | `requireVerify` 登记核对函数。读数是候选，写锁认可后才写缓存。一致时返回 `{ same: true, commit }`，`commit` 第一行同步检查读数是否仍是最新，不是就返回 `false` |
| 成功提示、清草稿 | 只在 `commit` 里做 |
| 四态展示 | 文案用分工第 4 节的表。整体结论作标题，`lastFields` 逐字段列出 |
| 到期 | 订阅 `onForceReread`，命中自己的锁键就重读 202 和 210。草稿保留 |

核对数据和线上请求分开：`record204` 的 `target` 只放用户改了的字段，其余记 -1。不管 `build204` 按哪种策略组装，核对只看用户改了的字段。

可改项规则（在 `editBlock`）：
- `can_change = false`：控制类型不可切换。
- 露点设定和湿度设定二选一，只有当前控制类型对应的那个能改。
- 设备离线、210 `unsupported`、读数 `control_type = -1`、没有 204 权限、`features.freshAirWrite = 'off'`：面板只读（`control_type = -1` 时开关、风速也不能改，见 2.3 的裁定）。
- 设备开关为关时，只能改开关（回复前的默认，见 2.2）。
- 风速选项是 低（0）、高（1）、自动（2），不复用温控的 1–99 和 100。

验收：
- 下发只走 `writeCtrl(204)`；非白名单项目被写防护拦下。
- 没有改动时下发按钮禁用。
- success 后显示「已下发，正在核对…」，核对一致才提示已生效并清草稿。
- 未变化、无法核对、结果未知三种情况锁保持到一致或到期。
- 刷新页面后恢复的锁能由 `verifier204` 核对。

测试要点（vitest，对照 `thermostat` 的用例清单）：
- `build204`：两种策略各自的请求体；预检读数为 -1 的字段；`name` 原样带回。
- `editBlock`：上面每条规则。
- 流程：预检不一致不发；`checkSentRecord` 不过不发；确认后离开页面不发；claim 失败不发；503 code 14 算未下发；超时算结果未知。
- 核对：四态；`commit` 否决；候选读数只在认可后写缓存；到期强制重读后草稿还在。
- `writeLockSetup.test.ts`：204 核对器只注册一次、在组织数据就绪后注册。
- 写路径守护用例（同 `unified/__tests__/write-path.test.ts`）：`freshAir` 目录里除了 `source.ts` 的 `writeCtrl(204)` 没有别的写调用。
- Playwright（演示数据）：改值 → 确认 → 生效；取消确认草稿保留；全程没有 `/ctrl/` 请求。

基线：重录 `state-standalone12-fresh-air`、`state-standalone12-mode6-fresh-air`、`confirm-fresh-air-send`，共 3 张；按需新增「待下发」状态 1 张。

### 2.1 开关（P0 加入 `features`）

### 2.3 为什么默认用 echo

- 如果后端认 -1 为不变：带回当前值等于把字段设成它现在的值，结果相同。
- 如果后端不认 -1：传 -1 会把露点设成 -1°C、把控制类型设成「都不可控」。带回当前值没有这个问题。
- 所以答案未知时，带回当前值在两种情况下都不出错，传 -1 只在一种情况下不出错。
- 代价：从读到发之间如果有人在屏上改了别的字段，会被带回的旧值盖掉。预检在发送前刚读过，窗口是一次请求的时间。
- 201 当时的结论是「不变传 -1」，后端也说过「所有设置接口不变项都传 -1」。这句话如果确认覆盖 204 的全部字段，就把默认值改成 `minus1`，和 201 一致。

Fable 11/25 裁定（A1 后端答复之前）：
- 用户没改的设定项（`control_type`、`dew_point`、`humidity_set`、`wind_speed`）如果在确认后新读的 210 里是 -1（或 65536 等无效值），这次**整条不下发**，提示「有未初始化的设定项」。不能只跳过那一个字段：跳过后 proto3 编码出来是 0，等于把它设成湿度控制、低档或 0°C。
- 读数 `control_type = -1` 时，写入口直接禁用。
- 实现在 P0 的 `blocked204`；`build204` 和预检都先调它。`switch` 没改时仍按 proto 传 -1，不在此列。
- 影响：11/25 实测 260911001 的 `humidity_set = -1`（见 `docs/api/实测记录-1125-新风天气.md`），这台设备在后端答复 A1 或把湿度设定初始化之前，只改风速的 204 也会被拦下。

## 3. S7 待后端确认的点

### 3.1 城市选择

原方案按字面做的结果：平台账号在测试服只有无锡、苏州两个城市；经销商调 city-list 是 403，没有城市可选。

改成三层：
1. 候选全集是本地省市级联数据。天气接口接受任意国标行政区划码，实测上海、北京、昆山都能查到，这些城市都不在 city-list 里。
2. city-list 只做过滤，按 `weatherCityFilter`：
   - `auto`（默认）：有权限且调用成功、返回非空，就取交集；没权限、失败或返回空，就不过滤。
   - `intersect`：严格取交集，调用不了时只剩第 3 层的城市。
   - `none`：不调 city-list。
3. 项目所在城市始终可选，不受过滤影响。来源是当前账号可见项目的 `region`，取市级码，去重后放在选择器最上面一组。

默认城市的取值顺序：缓存的上次选择 → 当前项目所在城市 → 可见项目里第一个有 `region` 的 → 候选里第一个 → 都没有就显示「请选择城市」。

需要负责人确认：首页天气要不要严格取交集。city-list 看起来是「有历史天气记录的城市」，是数据平台气象记录页的约束，对实时天气不是必要条件。确认要严格取交集就把默认值改成 `intersect`，同时后端要给经销商开 city-list 权限、正式服返回全量。

### 4.5 按屏加锁的影响

两个测试项目共用控制屏 `667b7cc6…`，锁键相同：
- S10 对 260911001 下发后，240829001 的温控页和统一控制同时被锁。核对一致时几秒放开；不一致时锁到到期，最长 2 分钟。
- 反过来，240829001 上有温控或统一控制的下发在进行时，S10 点下发会得到 busy。
- 按上面「success 但读数不变」的现状，每次下发大概率锁满 2 分钟。一个时段 2 次下发，同屏的其他测试要让出约 5 分钟。
- 别的账号在这块屏上的锁，本账号只看到「其他账号正在下发」，看不到项目名。
- 锁跨标签页同步。测试时不要在另一个标签页开着同屏项目的下发页做别的操作，容易把 busy 误判成故障。
- 刷新页面后锁会恢复。S10c 没合并时，恢复出来的 204 锁没有核对器，只能等到期。所以 204 核对器和下发界面必须在同一个 PR 里上线。
